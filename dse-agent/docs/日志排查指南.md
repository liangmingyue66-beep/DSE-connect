# 日志排查指南（怎么用日志定位 bug）

> 一句话：**系统不是黑盒**。一次对话会留下几行结构化 JSON，从"谁被调用、传了什么、返回什么"全都在里面。
> 排查任何问题的动作都一样：**先拿到 trace_id，再把这条 trace 的日志按顺序读一遍。**

---

## 一、日志长什么样、在哪看

每行一条 JSON，打到**服务进程的 stdout**（你启动 `uvicorn` 的那个终端窗口，或者后台任务的输出）。

```json
{"trace_id":"536e846b","span":"llm.chat","latency_ms":2438,"input_tokens":2061,"output_tokens":82,"tools":["query_schools_tool"],"answer_chars":64}
```

| 字段 | 含义 |
|---|---|
| `trace_id` | 一次请求的身份证（同一个请求的所有日志，这 8 位相同） |
| `span` | 这个事件是什么（下面有清单） |
| 其余字段 | 该事件的细节 |

**为什么用 JSON 而不是自然语言**：可以直接 `grep`、可以用 `jq` 过滤，也可以以后直接接日志系统，不用改埋点。

---

## 二、现在有哪些 span（系统在哪些环节留了痕迹）

| span | 什么时候打 | 关键字段 | 主要在排查什么 |
|---|---|---|---|
| `llm.chat` | 每次调模型 | `latency_ms`、`input/output_tokens`、`tools`、`answer_chars` | 模型想了多久、决定调哪个工具、有没有直接回答 |
| `tool.call` | 每次执行工具 | `tool`、`args`、`result`、`latency_ms` | **模型实际传了什么参数、工具返回了几条** |
| `llm.fallback` | 主模型失败切备用 | `primary_error` | 是不是偷偷降级到 DeepSeek 了 |
| `score.mismatch` | 分数与用户原话对不上 | `scores`、`user_text` | 模型抄错分数被拦住 |
| `param.province_cleared` | 省份/城市冲突被程序清空 | - | 多轮条件是否按预期清理 |
| `auth.rejected` | 会话凭证校验失败 | `reason` | 前端凭证过期/被篡改 |
| `session.busy` | 同一会话并发，排队超时 | `session_id` | 用户连点两次 |
| `session.sweep` | 后台清理过期会话 | `removed`、`alive` | 内存是否在回收 |
| `client.disconnected` | 客户端断开 | `session_id` | 关页面后是否停止生成 |
| `error` | 异常 | `error_type`、`detail` | 报错详情（用户只看到"出了点问题"） |

## 三、一次正常请求的"故事"（真实日志）

用户说"我434想去广东读计算机"：

```
{"trace_id":"536e846b","span":"llm.chat","latency_ms":2438,"tools":["query_schools_tool"],"answer_chars":64}
{"trace_id":"536e846b","span":"tool.call","latency_ms":335,
 "args":{"province":"广东省","major_keywords":["计算机"],"scores":["4","3","4"]},
 "result":{"total":6,"shown":6}}
{"trace_id":"536e846b","span":"llm.chat","latency_ms":11826,"tools":null,"answer_chars":783}
```

**逐行读**：

1. 模型想了 **2.4 秒**，决定调 `query_schools_tool`（`tools` 非空 = 要调工具）；
2. 工具执行 **335 毫秒**，参数是「广东 + 计算机 + 434」，返回 **6 条**；
3. 模型再想 **11.8 秒**，这次 `tools: null`（不再调工具）→ 写出 **783 字** 回答。

**这三行就是一次请求的全貌**。任何"答得不对"的问题，先看这三行在哪一步偏离了预期。

## 四、五类常见 bug 的排查路径

### ① 答非所问 / 答得太泛

**看**：第一行 `llm.chat` 的 `tools`。

- `tools: null`（没调工具就直接答）→ 模型跳过了查库，看 prompt / 护栏有没有拦住；
- `tools: ["search_policy_tool"]`（问分数却查政策）→ **选错工具**。

### ② 明明有数据却查不到（0 条）

**看**：`tool.call` 的 `args` 和 `result.total`。

```
"args":{"school_names":["湖南大学、中南大学"]}   ← 两个校名挤成一个元素
"result":{"total":0}                              ← 于是 0 条
```
这类问题的特征：**参数看起来"像对的"，但结构错了**。所以要看 `args` 的实际结构（数组？字符串？有没有多填的参数）。

### ③ 模型编造分数

**看**：有没有 `tool.call`。

- 整条 trace 里**没有 `tool.call`**，但回答给了具体分数 → 编造（护栏应当拦截并产生第二轮）；
- 有 `tool.call` 但 `result.total = 0`，回答却有分数 → **查空了还编**（护栏的第二个触发条件）。

### ④ 多轮对话条件继承错了

**看**：第二轮 `tool.call` 的 `args`。

```
第1轮 args: {"city":"上海市","major_keywords":["计算机"]}
第2轮 args: {"school_names":["中南大学","湖南大学"],"city":"上海市"}   ← city 没清掉！
```
**参数继承是"第二轮凭空多出一个旧条件"**，只看最终回答是看不出来的，必须看 args。

### ⑤ 报错 / 变慢

- **报错**：搜 `"span": "error"`，看 `error_type` + `detail`（用户只看到"出了点问题"，详情在日志里）；
- **变慢**：把 `llm.chat` 的 `latency_ms` 加起来。一次对话通常 2 次 LLM（决策 + 组织回答），如果出现 4-5 次，说明**护栏在反复驳回重查**（`answer_guard` 重试）。

## 五、实操命令（Windows / Git Bash）

```bash
# 1) 只看某一次请求的全部日志（把 trace_id 换成你的）
grep 536e846b 服务日志.txt

# 2) 只看工具调用（想知道模型传了什么参数）
grep '"span": "tool.call"' 服务日志.txt

# 3) 只看报错
grep '"span": "error"' 服务日志.txt

# 4) 只看 0 条结果（排查"为什么查不到"）
grep '"total": 0' 服务日志.txt

# 5) 数一数某次请求调用了几次模型（多了说明在反复重试）
grep 536e846b 服务日志.txt | grep -c 'llm.chat'
```

> 如果服务是跑在后台任务里，直接在任务输出里搜；如果想留存，把启动命令改成
> `... --port 8000 2>&1 | tee logs/server.log`。

## 六、没有日志时怎么办（补救手段）

日志只能看到"调了什么、传了什么"，看不到模型"为什么这么想"。当日志不够时，用**复现脚本**：

```python
from app.graph import graph
from langchain_core.messages import HumanMessage

st = graph.invoke({"messages": [HumanMessage(content="你的问题")], "memory": {}})
for m in st["messages"]:
    if getattr(m, "tool_calls", None):
        print("调工具:", [(t["name"], t["args"]) for t in m.tool_calls])
    elif m.type == "tool":
        print("工具返回:", m.content[:200])
    elif m.type == "ai":
        print("模型说:", (m.content or "")[:100])
```

**这是最有力的排查方式**：把 `state["messages"]` 整条打印出来，就能看到"模型每一轮说了什么、调了什么、拿到什么"。

## 七、这套日志的短板（诚实说明）

| 短板 | 影响 | 怎么补 |
|---|---|---|
| 服务走 `astream` 时 token 统计为 0 | `input_tokens/output_tokens` 不可信（成本分析失真） | 已知问题，未修（可开 `stream_usage=True`） |
| 只在 stdout，不落盘 | 重启就没了，无法回溯历史 | 生产应接日志文件/ELK |
| 没有记录"模型原始回答全文" | 定位"它为什么这么说"要看复现脚本 | 用上面的脚本，或加采样落盘 |
| 只有 8 位 trace_id | 极低概率碰撞 | 够用；正式环境用全量 UUID |

---

## 八、一句话总结

> **排查 bug 的动作永远是：找到那次请求的 trace_id → 按时间顺序读 `llm.chat` / `tool.call` → 看它在"哪一步偏离了预期"。**
> 不用猜，也不用读代码。
