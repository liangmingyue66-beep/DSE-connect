# 并发优化记录：从"同步阻塞"到"真异步"

> 这是一次**完整的工程排查记录**：现象 → 诊断 → 根因 → 方案 → 踩坑 → 验证。
> 面试时可以按这个顺序讲，每一步都有可复现的数据。

---

## 一、起因（现象）

用户在一个会话生成过程中切到另一个会话发消息，出现两种异常：

1. **前一版（已修）**：什么都没发生、也没有报错——那是前端 `streaming` 全局状态导致的**静默 return**，属于另一类问题，见复盘 #71；
2. **修完前端后**：两个会话能各自发送了，但用户的直觉是"两个一起发会不会互相拖累"。

实测（两个**不同会话**并发请求）：

```
总耗时 6.3s
  会话A: 6.3s（单独跑只需 2~3s）
  会话B: 3.7s
```

**A 被明显拖慢**，但又不是完全串行（完全串行应该是 10s）。

---

## 二、诊断（怎么定位到"同步阻塞"）

### 第一步：怀疑点

服务是 `async def gen()` + `graph.astream(...)`，看起来是异步的。但图里的节点是：

```python
def agent(state):                              # ← 同步函数
    resp = _invoke_llm_with_fallback(...)      # ← 内部 ChatOpenAI.invoke()，同步 HTTP
```

异步服务 + 同步阻塞调用 = **事件循环被占用**。

### 第二步：为什么"退化但不完全串行"

LangGraph 对同步节点会自动丢进线程池执行，所以不会彻底卡死事件循环；但线程池有容量、有上下文切换开销，并发一多就出现"部分串行"。

**这种退化不报错、不抛异常，唯一表现是"变慢"**——是最难被发现的一类性能问题。

### 第三步：为什么真实 API 测不准

用真实 Qwen API 测并发，数据在 2.4s ~ 5s 之间跳：

```
第一次：总 6.3s（A 6.3 / B 3.7）
第二次：总 8.07s（A 8.07 / B 4.6）
基线：4.96s
```

**上游 API 响应时间抖动比并发差异还大**，导致无法得出可靠结论。

### 第四步：用固定延迟假模型隔离上游

把 LLM 换成一个"固定 sleep 1.5s"的假对象，就能纯粹测"图执行层"的并发能力：

```python
class FakeLLM:
    async def ainvoke(self, messages):
        await asyncio.sleep(1.5)      # 异步：让出事件循环
        return AIMessage(content="mock 回答")

class BlockingLLM:
    async def ainvoke(self, messages):
        time.sleep(1.5)               # 阻塞：独占事件循环
        return AIMessage(content="mock 回答")
```

结果（`asyncio.gather` 同时跑两个）：

| 实现 | 两条并发总耗时 | 说明 |
|---|---|---|
| **异步**（`await asyncio.sleep`） | **1.51s** | 真并行，等于单条耗时 |
| **阻塞**（`time.sleep`） | **3.00s** | 完全串行，等于两条之和 |

**这组数据直接证明了"阻塞会让并发退化成串行"，而且排除了上游波动。**

---

## 三、根因

```
请求进来
  → 事件循环（单线程）
    → agent 节点（同步 def）
      → 线程池里执行
        → ChatOpenAI.invoke() 同步 HTTP，占着线程干等 3~10s
          → 其他请求只能等线程 / 等事件循环
```

两个具体阻塞点：

| 阻塞点 | 位置 | 类型 |
|---|---|---|
| **LLM 调用** | `_invoke_llm_with_fallback` 里的 `.invoke()` | 同步 HTTP（占 90% 时间） |
| **工具调用** | `query_schools_tool.invoke()`（psycopg2 查库）、`search_policy_tool`（httpx 调 embedding） | 同步 C 库 / 同步 HTTP |

---

## 四、方案（改了什么）

### ① LLM 调用改成异步

```python
async def _invoke_llm_with_fallback(messages):
    try:
        return await _llm_with_tools.ainvoke(messages)          # 异步 HTTP
    except Exception as e:
        observability.log_event("llm.fallback", ...)
        return await _llm_with_tools_backup.ainvoke(messages)   # 降级也走异步
```

```python
async def agent(state):
    resp = await _invoke_llm_with_fallback(_to_api_messages(state))
```

### ② 工具调用丢到线程池

psycopg2 没有异步版本，只能"挪走"而不是"改异步"：

```python
async def call_tools(state):
    ...
    result = await asyncio.to_thread(query_schools_tool.invoke, args)
    ...
    result = await asyncio.to_thread(tool.invoke, args)
```

**为什么两步都要做**：只改 LLM，查库那 300ms 仍会卡住事件循环；两处都改，事件循环里才没有阻塞调用。

---

## 五、踩的坑（这部分最能体现"改核心链路"的代价）

### 坑 1：同步 `graph.invoke` 调不了 async 节点

改完立刻报错：

```
TypeError: No synchronous function provided to "agent".
Either initialize with a synchronous function or invoke via the async API (ainvoke, astream, etc.)
```

**影响面**：`server.py` 用的是 `astream`（没问题），但 **`eval/run_eval.py` 和 `app/main.py` 用的是同步 `invoke`**，会全部挂掉。

**修法**：两处改成 `asyncio.run(graph.ainvoke(...))`。

```python
# eval/run_eval.py
state = asyncio.run(graph.ainvoke({"messages": messages, "memory": memory},
                                  config={"recursion_limit": RECURSION_LIMIT}))

# app/main.py（CLI）
state = asyncio.run(graph.ainvoke({"messages": messages, "memory": memory}))
```

> **教训**：改节点的同步/异步属性，是"影响全库调用方式"的改动。**先 grep 所有调用点**（`graph.invoke` / `graph.stream`），否则改完以为是 bug，其实是调用方式不对。

### 坑 2：验证方式本身会骗人

一开始用真实 API 做前后对比，结论是"改完更慢了"（6.3s → 8.07s）——完全是上游抖动造成的假象。

**必须用固定延迟的假模型**，才能把"代码层并发能力"和"上游响应时间"分开。

> **教训**：性能对比要先隔离变量。用真实外部依赖做 A/B 测试，测到的往往是外部系统的波动。

---

### 坑 3：`asyncio.run` 每条用例调一次 → `Event loop is closed`

第一版改法是"每条用例各自 `asyncio.run(...)`"，结果回归 **20/32**，失败的全是：

```
运行异常：Event loop is closed
```

**原因**：`asyncio.run` 每次都会**新建并关闭一个事件循环**；而 `ChatOpenAI` 的异步 HTTP 客户端（httpx.AsyncClient 连接池）在第一次调用时创建、绑定在**第一个**循环上，循环关闭后连接失效，后续用例复用它就报错。

**修法**：**整个评测/REPL 只用一个事件循环**。

```python
# eval/run_eval.py —— main 只 asyncio.run 一次，循环体移到 async 函数里
def main() -> int:
    ...
    return asyncio.run(_run_cases(cases, args.out))

async def _run_cases(cases, out_path):
    for case in cases:
        actual = await run_agent(case["input"])     # 注意是 await，不再每条 run 一次
```

```python
# app/main.py —— 整个 REPL 包成一个 async 函数
async def _repl():
    while True:
        user = (await asyncio.to_thread(input, "你：")).strip()   # input 也放线程
        state = await graph.ainvoke(...)

def main():
    asyncio.run(_repl())
```

> **教训**：**"异步"是有生命周期的**——HTTP 客户端、连接池、线程池都绑定在创建它的那个事件循环上。
> 在异步框架里，**一个入口只应该有一个事件循环**；把 `asyncio.run` 散落在循环体里，等于每轮都重建一套连接设施。

## 五、结果

| 验证项 | 结果 |
|---|---|
| 同步入口（eval / CLI） | ✅ 改用 `asyncio.run(graph.ainvoke(...))` 后正常 |
| token 级流式 | ✅ 单条对话仍产出 107 个 stream 事件 + 1 个工具状态事件 |
| 单测 | ✅ 30 个全过 |
| 回归（32 条：查询/意图/多轮/政策） | ✅ 32/32（见 `eval/run_async2.log`） |
| **并发能力（假模型，1.5s 延迟）** | ✅ **两条并发 1.51s**（改造前同类实现 3.00s） |

真实 API 下的并发收益会被上游限流/排队掩盖，但在**本地或低延迟模型**（如本地部署的 Qwen）场景下，收益是线性的。

---

## 七、结论与可讲的三句话

1. **"异步服务里混进同步阻塞调用，会让并发静默退化成串行"**——不报错、不告警，只表现为变慢，这是最难查的性能问题；
2. **"改异步要连带改调用方"**——LangGraph 的同步 `invoke` 无法驱动 async 节点，必须全库排查调用点（评测脚本、CLI 首当其冲）；
3. **"异步有生命周期"**——HTTP 客户端/连接池绑定在创建它的事件循环上，`asyncio.run` 散落在循环体里会导致 `Event loop is closed`；
4. **"性能验证要隔离变量"**——外部 API 的抖动比你要测的差异还大，用固定延迟的假模型才能测出代码层的真实并发能力。
