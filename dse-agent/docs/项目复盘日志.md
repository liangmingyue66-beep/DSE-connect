## 四、关键设计决策（面试可讲）

1. **架构：混合（ReAct 循环 + 确定性工具内核）**——2026-10-17 从"显式状态机"转向。查分数用确定性工具（query_schools，模型不算数），整体对话用 ReAct 循环（模型自由决策调工具/追问/回答）。**关键教训：'数据准确'靠'确定性工具 + 防模型绕过工具编'，不靠'工作流 vs ReAct' 的选择；出错代价高→确定性工具，代价低→模型自由。**
2. **浅层 Agent（路由型）定位**：LLM 只做意图翻译，自主度最低档，离工作流一步之遥——这是**正确取舍**，不是偷懒（分数线查询必须精确可验证）。
3. **LLM 不计算、不编造**：筛选/排序/分页/分档/收尾全由代码做，模型只做"意图翻译 + 自然语言转述"。
4. **模型可替换可降级**：依赖隔离在 `llm.py`，Qwen 主 + DeepSeek 备。
5. **记忆分层**：短期（会话内 memory）已实现；长期（跨会话）未做，做时必须配失效策略（只留最近 N 轮/摘要），否则"永不结束"导致上下文爆炸。
6. **可观测性**：已做命令行雏形（意图/槽位/工具/耗时）；完整版（trace_id+结构化日志+指标）待 P5。
7. **State 与 Model 分离（防 LLM 抄写错误）**：精确的结构化状态（查询条件、分数）由代码持有（memory），LLM 只做"理解意图 + 提取本轮增量"，绝不从历史文本抄写精确值。这是 Agent 工程基本功——**可信状态归确定性系统，LLM 归推理**（对应 LangGraph checkpoint、生产环境"关键数据存库让模型用工具查"同一思想）。

## 六、方法论反思：打地鼠式开发的三个根因（2026-10-17）

> 背景：做 extract 槽位时，接连"补丁式"处理了拆词、转全称、门类展开、别名……被用户追问"难道要猜到用户所有问题吗"，反思出三条根因。

1. **动手前没做"输入空间梳理"（最根本）**：没先枚举"用户查学校可能有哪些表达类型"（单专业/并列/简称/门类/院校群/成绩说法），把"同一个问题（口语→规范名语义对齐）"当成了"一堆不同问题"逐个打补丁。
2. **"限制 vs 信任模型"无稳定原则，被情绪驱动**：把"不让模型抄精确值"（对）过度推广成"不让模型做任何知识输出"（错），把模型该做的语义理解也锁死了。
3. **局部修补压过了抽象**：每个补丁单独都对，但在"具体表达"层解决，而非"语义归一化"层一次性解决。

> 教训：Bug 出现先"问五个为什么"追到设计环节，别急着补表达；动手前先系统梳理输入空间。正解是"让模型统一做语义归一化 + 代码兜底"。
