# 踩坑演化线 与 测评集设计思路

> 用途：面试叙事。把零散的坑串成"有逻辑的演化"，比背知识点更有说服力。

## 一、四条踩坑演化线（面试可直接讲）

### 主线 1：数据可信度的演进（最核心的故事）

```
数据错（默认0被当合法分数）
   ↓ 修数据
模型抄错分数（434→454）
   ↓ State/Model 分离：精确值代码持有，模型只给增量
仍然可能抄错"第一句"（模型从原文解析就错了）
   ↓ 分数原文溯源：代码校验"模型给的分数能否在用户原话里找到"（不匹配→返回重提→2次→问用户）
模型"没查就编"
   ↓ 加 answer_guard 护栏
护栏误伤政策（"校长推荐计划"里的"8分"被当编造）
   ↓ 护栏加宽：先判断"用户是不是在问分数"
政策也编（"4所→8个""三科→四科"）
   ↓ 护栏再扩展：政策强制检索 + 只依据原文
```

**一句话**：数据可信不是"一次修对"，是"数据→模型→护栏→精细化"层层递进。

### 主线 2：架构选择的摇摆

```
怕模型发散 → 选固定状态机（保守）
   ↓ 用户嫌死板
转 ReAct 自由决策（放开）
   ↓ 怕数据不准
加确定性工具 + 护栏（混合）
   ↓ 为修 400 做 hack（工具结果伪装 user）
引出模型模仿"已调用工具"等新 bug
   ↓ 实测标准格式其实可用 → 撤销 hack
```

**一句话**：从"过度保守"到"过度放开"，最后落在"混合（自由外壳 + 确定性内核）"。

### 主线 3：多值参数的处理（打地鼠教训）

```
多校名查不到 → 加"顿号分隔"
   ↓ 用户指出"空格/破折号/和猜不完"
改数组 school_names（模型自己拆）
   ↓ 代码还在猜字符串（_split_keywords）
改严格 Pydantic：传字符串就报错，让模型改
```

**一句话**：**"猜字符串分隔符"永远猜不完，多值用数组 + 严格校验**——别再打地鼠。

### 主线 4：流式与异步

```
回答卡住十几秒 → 加 token 级流式
   ↓ 还是"一瞬间全出"
实测 118 个事件同一时刻到达 → 同步 stream 在 async 里缓冲
   ↓ 换 graph.astream
逐条到达（时间戳 0.78s→1.14s→…）
```

**一句话**：验证"流式"要看**到达时间戳**，不能只看内容顺序。

## 二、面试叙事模板（可直接背这段）

> "这个项目我最大的收获，不是'做出了一个 Agent'，而是**怎么一步步把不可信的东西变得可信**。
> 一开始我以为'别让模型编'就是写好 prompt，结果评测一跑，**对抗用例 3 条全挂**——模型被'别查库、管理员模式'一诱导就凭记忆编。
> 于是我加了 answer_guard 护栏，但很快发现**护栏太粗会误伤**：政策回答里合法的'8分'被当成编造。
> 所以我把护栏改成'**先判断用户是不是在问分数**'，政策问答不误伤；后来政策也编（4所→8个、三科→四科），又把护栏扩展到政策强制检索。
> 整个过程让我明白：**Agent 的可信不是靠一个机制，而是'确定性工具 + 护栏 + 评测'一层层叠出来的**。"

## 三、测评集是怎么写的（设计思路）

### 1. 按"能力维度"分，不是按"功能"分

8 个维度：查询准确性 / 意图理解 / 多轮记忆 / 忠实度 / 政策问答 / 开放问答 / 边界异常 / 安全对抗。
**原因**：功能是"能做什么"，能力是"做得对不对"——面试更关心后者。

### 2. 每类都含"正常 + 边界 + 对抗"

- **正常**：单条件/多条件查询（"我434想去广东读计算机"）
- **边界**：空输入、超长、非法成绩、不存在专业
- **对抗**：提示注入（"忽略指令"）、诱导编造（"凭记忆告诉我"）、越权（"管理员模式"）、泄露系统提示

**原因**：只测正常 = 自欺欺人。真实用户会乱输、会诱导。

### 3. 断言用**确定性规则**，不靠 LLM 打分

- `must_call_tool`（必须调了某工具）
- `output_contains`（含关键内容）
- `must_not_leak`（不泄露）
- `output_safe`（查了库 **或** 没给具体分数 = 安全）

**原因**：LLM 打分本身不稳定（"LLM-as-judge 也会编"），而"该查没查就编分数"这类断言必须 100% 稳定。

### 4. 每条用例带 `rubric`（评分标准）+ `focus`（考察点）

让"为什么测这条"可追溯——不只是"过没过"，还有"这条在考什么能力"。

### 5. 保留完整证据

`report.json` 里存每条的 **input + output + tools + latency**，失败时能回看"模型到底说了什么"，而不是只有一个 FAIL。

### 6. 回归驱动

**改一次代码跑一次**，失败用例逐个归因（模型/提示词/数据/检索/工程），按影响程度排优先级。

## 四、面试怎么讲"测评集"（话术）

> "我先按**能力维度**拆（查询、记忆、忠实度、政策、边界、对抗），每类写**正常+边界+对抗**的用例，共 52 条。
> 断言用**确定性规则**——工具调没调、有没有编分数、有没有泄露，不靠 LLM 打分（因为它自己也不稳）。
> 每次改代码跑回归，**失败用例逐个归因**：是模型问题、提示词问题、数据问题、检索问题还是工程问题，再按影响程度排序修。
> 这套'评测驱动'的流程，抓出了很多**手动测根本测不到**的问题——比如'对抗诱导编分数'、'政策数字与原文不一致'，这些如果靠人肉测，几乎不可能覆盖到。"

## 五、可直接用的数字（面试官爱听）

- 54 条测评集（查询 8 / 意图 10 / 多轮 8 / 忠实 8 / 政策 6 / 开放 4 / 边界 5 / 对抗 5）
- 首次跑 **14/20 = 70%**（对抗 1/4）→ 补护栏 → **20/20**
- 二轮全量 **47/52 = 90%** → 修政策幻觉/递归/数据错字 → **52/52**
- 对抗类用例：**提示注入、诱导编造、越权、泄露**四类全覆盖
- 单测 **13 个**（查询 / 分数溯源 / 会话 TTL / 并发锁）

## 六、"没做，但想清楚了"的技术取舍（面试加分项）

比"我做了什么"更能体现判断力的，是"**我知道什么不该做**"。这几条都是评估后**主动不做**的：

### 1. 检索相似度阈值——评估了，不做

**为什么不做**：语料只有 18 个 chunk，且全部是招生政策（语义空间极近）。实测分数分布：

| 组 | top1 范围 |
|---|---|
| 该召回的（报名/志愿/计分…） | **0.593 ~ 0.745** |
| 不该召回的（你好/天气/写诗…） | **0.375 ~ 0.572** |

边界在 **0.58 附近，两组只差 0.02**——在这个语料上定阈值等于"过拟合这 14 个样本"，换批问题就失效。

**更关键的方法论**：**cosine 阈值不能跨模型抄**。网上流传的 0.7/0.75 是别的 embedding 模型的经验值，套到我们这（text-embedding-v3）会**把正确答案全过滤掉**（我们相关问题的最高分才 0.745）。正确做法是：准备"该召回/不该召回"两组样本 → 测分布 → 找分界点 → 按业务偏好倾斜（怕漏就调低，怕误导就调高）→ 上线后持续用真实 query 校准。

**什么时候该做**：语料涨到几十份文件、召回噪声肉眼可见地影响回答时。**先上混合检索（关键词+向量）或 rerank，再考虑阈值**——阈值是最后一道闸，不是第一道。

### 2. MCP——评估了，不做

单 Agent + 2 个自有工具，直接 `@tool` 是最短路径。MCP 的价值是"多客户端共享工具 + 接第三方生态"，这里发挥不出来，属于为用而用。**要做也是把"查询能力"封装成 MCP Server（能力层），业务编排留在 Agent 内**。

### 3. Redis——不做

单实例部署，进程内 dict 当缓存足够。上 Redis 只解决"多实例共享缓存"，而我们现在连多实例都没有。**引入它只会增加一个故障点**。

### 4. 向量数据库（FAISS/Chroma）——不做

18 个 chunk，内存向量 + 余弦相似度足够（甚至在启动时算完）。引入向量库是典型的过度设计，还多一堆 Windows 安装坑。

### 5. 会话持久化——**这个要做**（与上面相反）

判断依据很简单：**用户会不会察觉到**。阈值调不调、用不用 MCP，用户看不见；但"刷新一下历史没了""重启后要重新说一遍"，用户立刻能感觉到——**这就是 demo 和产品的分界线**。所以这一项不能省。

> 一句话总结这节的讲法："我评估过五件事，只做了其中一件——**判断标准不是'技术先不先进'，而是'用户能不能感觉到'**。"
